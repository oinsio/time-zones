# Design

## Context

See `proposal.md` for the motivation. What exists today, read from the code:

- The service worker is generated by `vite-plugin-pwa` with `registerType: "prompt"` (`vite.config.ts`). In this mode the new worker does not skip waiting on its own: it installs, precaches the new build and waits. `usePwaUpdateStatus` wraps `useRegisterSW`; `needRefresh` becomes `isUpdateAvailable`, `applyUpdate` posts skip-waiting and reloads, `dismiss` sets `needRefresh` to false. `AppShell` shows `UpdateNotice` while `isUpdateAvailable`.
- A waiting worker becomes active by the browser's own rule once no window is controlled by the old worker, so the first start after every window was closed runs the new build. A reload of a single window does not: the old worker keeps the client. This is standard service worker behaviour, not Workbox configuration; nothing in the project changes it.
- `useRecheckOnReturn` schedules the update recheck (page visible again, at most once per 15 minutes) for both the service worker check (`useUpdateRecheckOnReturn`) and `useZoneRulesUpdate`.
- `useZoneRulesUpdate` stores a newer release and reports its name as `readyRelease`; `ZoneRulesUpdateNoticeSlot` shows the notice and chooses `applyUpdate` over a plain reload when `isUpdateAvailable`. "Active release at start" already makes a newer stored release active at the next start, notice or not.
- The build fixes one value into the code already: `__APP_DEPLOY_INSTANT__` from `scripts/deployInstant/`, exposed as `APP_DEPLOY_INSTANT` (`src/constants/deploy.ts`). `zoneRulesPlugin` emits `zone-rules/version.json` and the release file; `vite.config.ts` keeps them out of the precache with `globIgnores`; `fetchZoneRulesVersionSource` reads the version file with `cache: "no-cache"`.
- The committed city data records `source.dumpDate`, but `toServedCityData` drops `source`, so the client does not know the date. `CityDataAttribution` renders one translated link.
- CI checks out with `actions/checkout@v5` at its default depth of one commit in the `check` job of `.github/workflows/ci.yml`, so a build there sees one commit. Its step "Check data-only paths" runs `git fetch --no-tags --depth=1 origin main` before `pnpm build`. `deploy.yml` builds the published site by calling that workflow (`uses: ./.github/workflows/ci.yml`).
- The data-only commit is owned by `DATA_ONLY_TRAILER = "Data-Only: true"` in `scripts/dataRefresh/refreshConstants.ts` (glossary `docs/glossary/architecture.md`). Scripts inject child processes through the `RunProcess` type of `scripts/zoneRules/processTypes.ts`, as `scripts/cityData/compile.ts` does.
- `src/app/AppShell.tsx` has 199 lines. `playwright.bdd.config.ts` runs the projects `chromium`, `mobile-chrome` and the view-contract projects — no WebKit — against one build served by `pnpm build && pnpm preview`.

Constraints: no backend; the legacy iOS 12 build (ADR-0009) runs the same shell code, has `fetch` and no BigInt; iOS does not restart an installed PWA on its own (the reason the update recheck exists); the factory may not write `.github/`, `docs/adr/` or `CLAUDE.md`.

## Goals / Non-Goals

**Goals:**
- One discriminator, the app revision, decides the update notice; the client compares two opaque strings and knows nothing about commits.
- The zone rules comparison is a pure function of two releases, a set of zones and an instant, owned by the zone rules library.
- No new request, timer or formatter on the paths that run every minute or on every start without a waiting build.

**Non-Goals:**
- Changing the service worker strategy (`generateSW`, prompt mode) or adding a custom worker.
- Switching builds while the app is open.

## Decisions

### D1. The app revision is computed at build time from git, with an override (FR1)

`scripts/appRevision/resolveAppRevision.ts` (new, pure over an injected `RunProcess`) returns, in this order: the environment value `APP_REVISION` when set and not empty; else the first commit of `git log --format=%H%x00%(trailers:only,unfold)%x1e` from `HEAD` none of whose trailer lines equals `DATA_ONLY_TRAILER`; else a unique value built from the deploy instant (`unreadable-<instant>`). The trailer is imported from its owner, `scripts/dataRefresh/refreshConstants.ts`, never written a second time; only the format string and the prefix are new constants (`scripts/appRevision/constants.ts`). Nothing under `src/` knows the trailer. `vite.config.ts` passes the result as the define `__APP_REVISION__`; `src/constants/deploy.ts` exposes `APP_REVISION`; Vitest gets `TEST_APP_REVISION` from `app.config.ts`, like `TEST_DEPLOY_INSTANT`.

Why git and not a hash of the built files: the build embeds the deploy instant, so every build hashes differently; a hash of "code without data" would need a list of data files kept in step with the bundler. The trailer is one explicit statement by the author of the commit, human or bot.

Why the override: a version number set by a human later is `APP_REVISION=1.4.0` in the workflow, or a read of `package.json` in this one script. The client does not change (NG1).

Alternatives rejected: a list of data paths (`git log -- ':!city-data' ':!zone-rules'`) — the CLDR names arrive through `pnpm-lock.yaml`, which is not a data path; the commit that lands on `main` being unmarked by mistake errs on the safe side (a notice), a path list errs silently.

### D2. The revision is published as a file, read only while a build is waiting (FR2, FR3, FR5, FR6, NFR-P1)

A small Vite plugin next to `zoneRulesPlugin` emits `app-revision.json` (`{"appRevision":"…"}`) into the build root; its name joins `globIgnores`, and the precache check of `scripts/zoneRules/precacheExclusion.ts` gets a sibling for this file. A port `AppRevisionSource` (`fetchAppRevision(): Promise<string | AppRevisionFailure>`) has two adapters, `createFetchAppRevisionSource` (`cache: "no-cache"`, base URL from `import.meta.env.BASE_URL`) and an in-memory one for tests, both under one contract test, as `ZoneRulesVersionSource` has.

The page cannot ask the waiting worker what it holds without a custom worker, so it asks the site. The site always serves the newest build, and the waiting build is at least as old; if the two differ in app revision from the running build, an app change is on its way, which is exactly when a notice is right.

Alternative rejected: a custom service worker (`injectManifest`) answering a message with its revision — replaces the generated worker and its tests for one string.

### D3. `usePwaUpdateStatus` separates "a build is waiting" from "the notice is shown" (FR3, FR4, FR7, FR11)

The hook keeps the owner role for the update notice and returns:

- `isBuildWaiting` — `needRefresh` as the worker reports it, never cleared by a dismissal;
- `isUpdateAvailable` — `isBuildWaiting`, a published revision was read, it differs from `APP_REVISION`, and it is not the dismissed revision;
- `applyUpdate`, `dismiss` (records the published revision as dismissed), `isOfflineReady` as today.

The published revision is read when `isBuildWaiting` turns true and on each update recheck while it is true, in the same `onRecheck` that calls `registration.update()`; a failure keeps the last value read. `ZoneRulesUpdateNoticeSlot` takes `isBuildWaiting` instead of `isUpdateAvailable`, so its Reload applies a silent update too. `AppShell` passes the source. Because `AppShell.tsx` is already at 199 lines, the notices region moves into a new `src/app/AppShellNotices.tsx`, which takes the update status and the zone rules update and renders both notices; `AppShell` renders it.

A silent update needs no code: the hook simply does not show the notice and the worker stays waiting until the browser activates it at the next start (see Context). The page never calls skip-waiting for it. Skip-waiting without a reload was rejected: the old page would keep running old code while the precache of the old build is cleaned up, and its lazy chunks (views, search data) would fail to load.

### D4. Whether a release changes a zone is a pure function of the zone rules library (FR8, NFR-P2)

`src/lib/zoneRules/core/zoneRulesDifference.ts` (new): `hasZoneRulesChangeFrom(activeRules, storedRules, epochSeconds)` compares the local time type in force (`getLocalTimeType`, the existing owner: `utcOffsetSeconds`, `designation` and `isDaylightSavingTime`), the listed clock changes with `epochSeconds` greater than the instant, and the future rule, by value. `findChangedZones(activeRelease, storedRelease, zoneIds, epochSeconds)` applies it per zone; `ZoneRulesRelease.zones` already resolves links to their target's rules, so links need no special case; a zone in one release only is changed.

"From the instant on" and not "any difference": most IANA releases correct the past, and the release file is cut at the year 2000 anyway. A user can pick a past date in the calendar, so a corrected past offset would be shown wrongly until the next start; that is accepted as the price of silence (the next start uses the release in every case).

The abbreviation counts because the zone label can show it.

### D5. Watched zones come from the model; the hook compares on a key (FR9, FR10, NFR-P2)

`getWatchedZoneIds(state)` (new selector in `src/model/`) returns the distinct zones of `state.locations` plus `state.deviceTimeZoneId`. `useZoneRulesUpdate` takes `watchedZoneIds` and keeps the parsed stored release it already has in hand (`downloaded`, or `storedLoadResult.release`) in a ref. It recomputes "changes a watched zone" only when the stored release name or the sorted, joined zone ids change, with the clock's instant at that moment; `readyRelease` is reported only when the result is true. A minute tick changes neither key. `findChangedZones` reads each given zone once from each release, so the zones compared are exactly the ids passed to it; tests count them by wrapping the `@/lib/zoneRules` export with `vi.mock` (test helper `src/test/zoneComparisonCount.ts`), because a call inside one ES module cannot be spied and `src/test/workCounters.ts` has no counter of compared zones.

### D6. The dump date of the city data is a build constant, formatted by the presenter (FR12, FR13, NFR-P3)

The dump date already has owners: `readDumpDate` in `scripts/cityData/download.ts` (not exported) reads it from the archive entry time when the city data is compiled, and `checkFormat` in `scripts/cityData/checkCityData.ts` checks `source.dumpDate` of the committed file, today only as a non-empty text. No second reader or validator is written:

- Both functions below live in `scripts/cityData/committedDumpDate.ts` and nowhere else (`checkCityData.ts` has 180 lines and imports from it) — one module, one validation.
- `isDumpDate(value)` — a string equal to `Temporal.PlainDate.from(value).toString()`, `false` when parsing throws. The format check of `checkCityData.ts` imports it for `source.dumpDate`, so `city-data:check` rejects a dump date that is not an ISO date.
- `readCommittedDumpDate(cityDataText)` parses the committed file and returns `source.dumpDate`, throwing a message that names the dump date unless `isDumpDate` holds. Its name says what differs from `readDumpDate`: it reads the committed city data, not the archive.
- `vite.config.ts` calls `readCommittedDumpDate` on `city-data/geonames-cities.json` and defines `__CITY_DATA_DATE__`; `src/constants/deploy.ts` exposes `CITY_DATA_DATE`; Vitest gets `TEST_CITY_DATA_DATE` through the define of `vitest.config.ts`. `playwright.bdd.config.ts` has no Vite but loads `@/constants`, which re-exports `./deploy`, so its existing `Object.assign(globalThis, …)` also sets `__APP_REVISION__` and `__CITY_DATA_DATE__` from `TEST_APP_REVISION` and `TEST_CITY_DATA_DATE`, as it does for the deploy instant. The settings page must not load the search data to print one date, and the date must be right offline.

The concept gets the glossary term **Dump date** in `docs/glossary/search.md` (*Code:* `CityDataset.source.dumpDate`, `readDumpDate`, `isDumpDate`, `readCommittedDumpDate`, `CITY_DATA_DATE`).

`presentCityDataAttribution(language, translate)` (new, `src/presenter/`) formats the date with the cached formatter of the deploy date (`getDateTimeFormatter`, `DateTimeLabelKind.DEPLOY_DATE`) in `UTC_ZONE_ID`, so the calendar date does not shift with the device zone, and fills `settings.cityDataAttribution` (`"City data: GeoNames ({{date}}), CC BY 4.0"`). `CityDataAttribution` renders the text it is given.

Alternative rejected: a separate line. It would change the order rules of the deploy time and the zone rules release line for no gain; one line names source, date and licence.

### D7. CI gives the build its history (FR1)

Two edits in the `check` job of `.github/workflows/ci.yml`, both needed: the checkout gets `fetch-depth: 0`, and the step "Check data-only paths" fetches `main` without `--depth=1` (`git fetch --no-tags origin main`). With the first edit alone, that step's `git fetch --no-tags --depth=1 origin main` — which runs before `pnpm build` — records the fetched commit as a shallow boundary; on a push to `main` that commit is `HEAD`, so `git log` in `resolveAppRevision` sees one commit again and a data-only `HEAD` gets `unreadable-<instant>` and a notice. Without `--depth` the fetch adds nothing to a full clone, and `check-paths` diffs `origin/main..HEAD` (two dots, `scripts/dataRefresh/cli.ts`), which needs no merge base, so the path check is unchanged. `deploy.yml` calls this workflow, so with both edits the published build sees the history too. The factory may not edit `.github/`, so this is handoff patch H1. Until it is applied a CI build sees one commit: an app commit gives the right revision; a data-only commit gives the unique value and so a notice — the behaviour of today, never a wrong silence.

### D8. The silent update E2E serves two builds itself (FR3, FR4, FR11, M1)

The preview server of `playwright.bdd.config.ts` serves one build, and a waiting build needs a second one. A worker-scoped fixture of `app_shell_silent_update_e2e.steps.ts` (helpers in `src/test/features/app_shell/steps/silentUpdateSite.ts`) builds the app twice with `vite build --outDir <temporary directory> --emptyOutDir`: build A as is, build B with `APP_REVISION` set to the revision in A's `app-revision.json` (a silent update) or to another value (an app change). The deploy instant differs between two builds, so B has its own JavaScript, its own service worker and its own deploy time on the settings page — the observable proof of which build runs. A `node:http` static server in the fixture serves A or B under `APP_BASE_PATH` on its own port (`SILENT_UPDATE_E2E_PORT` in `app.config.ts`) and is switched by a step. Closing every page of the browser context and opening a new one is "every window closed". No production code exists for the test, and nothing is written inside the repository.

Alternative rejected: a build input that overrides the city data date for build B — it would exist only for one test.

## Risks / Trade-offs

- [A commit that changes code carries `Data-Only: true`] → users get code without a notice. Guarding the trailer (only on commits that touch data files) belongs to `refresh-data-through-scheduled-pull-requests`; this design assumes it.
- [Squash merges rewrite the commit message] → the trailer must be on the commit that lands on `main`. Assumed from the same change; if it is missing, the build errs towards a notice.
- [An installed PWA that is never closed keeps the old data] → accepted (NG2). Zone rules that change a watched zone still raise their notice.
- [Activation of a waiting worker at the next start is browser behaviour, not verified on iOS 12 here] → the E2E scenario "A silent update is in use at the next start" checks it in the Chromium projects, the only engines `playwright.bdd.config.ts` runs; Safari and iOS 12 are outside the automated matrix.
- [The site serves a newer app revision than the waiting build holds] → the notice appears and Reload brings the waiting build; the next check finds the newer one. One extra notice in a rare race.
- [Past corrections of a watched zone stay unannounced] → see D4.

## Migration Plan

No deploy order: the data refresh has landed, and until this change is deployed every data-only deploy shows the update notice, as today. The global decision (app revision, published file, watched zones) refines ADR-0014 point 5 and is recorded as a new ADR through handoff H2, not here. The first deploy of this change is itself an app change, so users see one last ordinary notice. Rollback: revert the change; the notices return to today's behaviour, the extra file is ignored.

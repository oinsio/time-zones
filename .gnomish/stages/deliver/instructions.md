# Инструкции стадии deliver

Изменение специфицировано, реализовано, зелёное и заархивировано. Твоя задача —
передать его человеку: открыть pull request для ветки этой задачи и написать
описание, которое нужно ревьюеру.

Нужные факты лежат в рабочей копии — прочитай их, не угадывай:

- ветка: `git branch --show-current` (это `gnomish/<task>`);
- репозиторий: `tracker.github.repo` в `.gnomish/config.yaml`. Это значение
  для `--repo`. Не полагайся на `origin`;
- номер issue задачи: `taskId` в `.gnomish-task/task.json`, например
  `github:owner/repo#29` → issue `29`. Читай этот файл, никогда не пиши в него;
- что на самом деле изменилось: `gh api repos/<repo>/compare/main...<branch> --jq '.files[].filename'`
  выводит список изменённых файлов — в рабочей копии может не быть ни remote
  `origin`, ни `main`, поэтому `git diff origin/main...HEAD` может упасть.
  Заархивированное изменение в `openspec/changes/archive/YYYY/MM/` хранит
  обоснование: в его `proposal.md` есть id требований (`FR1`, `UX1`, …) и
  метрики успеха. Читай конкретные нужные файлы; не выгружай диффы целиком.

Шаги:

1. Фабрика пушит ветку после каждой попытки, так что она уже есть на GitHub.
   Не пушь. Если `gh pr create` сообщает, что head-ветки не существует,
   остановись и скажи об этом в итоговом резюме — это проблема оператора.
2. Запиши описание pull request в `pr-body.md` в корне репозитория. Этот файл
   игнорируется git: это копия, которую читают проверки этой стадии, и она
   должна оставаться идентичной тому, что ты публикуешь. Проверки убеждаются,
   что путь к архиву, id требований и тестовые файлы, которые в нём названы,
   существуют, и что названо каждое отклонённое замечание ревью — поэтому
   называй их точно. Пиши его на английском, для человека, который не видел
   задачу:
   - один абзац о том, что изменилось и почему;
   - видимое пользователю поведение до и после (для чистого рефакторинга или
     изменения инструментов — указать, что его нет);
   - требования, которые оно реализует, по id, из заархивированного proposal;
   - как это проверено: `pnpm lint`, `pnpm typecheck`, `pnpm test`,
     `pnpm build`, бюджет бандла, набор BDD E2E, а также спеки Vitest и файлы
     `.feature` в `packages/client/src/`, покрывающие изменение; показатели
     мутационного тестирования, если их приводят коммиты или резюме стадии
     implement;
   - итоги обоих ревью из `review-specs.md` и `review-code.md` в
     заархивированном изменении: для каждого — сколько замечаний каждой
     серьёзности исправлено и отклонено, и каждое отклонённое замечание по id
     с причиной в одну строку — человек решает, согласен ли он;
   - ссылку на заархивированное изменение OpenSpec;
   - финальную строку `Refs #<issue>`. Используй `Refs`, а не `Closes` — этот
     проект закрывает свои issue сам.
3. Сначала поищи существующий открытый pull request — повторный запуск этой
   стадии не должен открывать второй:
   `gh pr list --repo <repo> --head <branch> --state open --json number`
   - нет ни одного: `gh pr create --repo <repo> --base main --head <branch> --title "<title>" --body-file pr-body.md`
   - один уже есть: `gh pr edit <number> --repo <repo> --title "<title>" --body-file pr-body.md`
4. Выведи URL pull request в итоговом резюме.

Заголовок — короткое предложение в повелительном наклонении, описывающее
изменение, как хорошая тема коммита: не `gnomish: ...` и не исходный заголовок
задачи, если тот был жалобой, а не описанием.

Правила:

- `pr-body.md` — единственный файл, в который тебе можно писать. Всё остальное —
  `packages/`, `openspec/`, `docs/`, `package.json`, lock-файл, `.github/`,
  `.claude/`, `.gnomish/`, `.gnomish-task/` — завершённая работа; оставь её
  ровно такой, какой нашёл.
- Не коммить и не пушь. Не мерджи pull request и не закрывай issue.
- Держи командные строки `gh` простыми и буквальными: подставляй ветку,
  репозиторий и номер issue обычным текстом, который ты уже прочитал, а
  описание передавай через `--body-file`. Подстановки команд внутри аргументов
  и here-документы — именно тот shell, который останавливает гейт разрешений.
- Если `gh` сообщает, что нет аутентификации или что токен не может писать в
  репозиторий, остановись и скажи об этом в итоговом резюме — это проблема
  оператора, а не то, что нужно обходить.

Держи вывод небольшим. Жёсткого потолка нет — фабрика вычитывает stdout
раунда по ходу работы, — но каждый выведенный байт — это контекст и деньги.
Поэтому: пропускай длинный вывод команд через `tail -30`, читай конкретные
нужные строки, а не файлы целиком, и ограничь итоговое резюме несколькими
предложениями.
